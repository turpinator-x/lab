Deep modules

The big picture

Software gets hard when you must hold too much in your head. Modules are how we hide things so we don't have to.

A module is anything with an interface (what callers must know) and an implementation (the code inside). Ousterhout's notes say the interface includes more than the signature. It includes side effects and behaviour callers depend on.

The goal, in his words: lots of functionality for little interface complexity.

Deep vs shallow

A deep module is easy to use and does a lot. A shallow module costs you nearly as much to learn as it saves you.

The classic example: files

Unix file I/O is Ousterhout's example of a deep module. A few calls (open, read, write, close) hide disk layout, caching and drivers. Devices are opened like files and use the same read and write calls (his Unix notes). The kernel handles device details, so callers never see them.

Warning signs: shallow modules

  • Calling it takes about as much code as doing the work yourself.
  • It just passes calls to something else.
  • You have classitis: many tiny classes, each hiding almost nothing.

Deletion test. Imagine deleting the module. If the complexity vanishes, it was a pass-through. If it reappears in many callers, the module was earning its keep. (Vocabulary from the codebase-design skill; the test is a rule of thumb, not Ousterhout's.)

One caution: size alone isn't the measure. Ousterhout says the real metric is functionality divided by interface complexity.
