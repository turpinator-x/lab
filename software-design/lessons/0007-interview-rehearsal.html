The six questions

1. What is a deep module? Give an example from your own work. (Lesson 1)

  • Small interface, lots of behaviour hidden behind it.
  • Claims-app: wallet address in, next claim time out. It hides the contract reads and network calls.
  • Deletion test: delete it and every user must solve that themselves. The complexity reappears in every caller.
  • Name one thing the caller still has to know, for honesty.

2. Why do you keep a glossary when you work with AI agents? (Lesson 3)

  • An agent reads your names. Two words for one thing invite wrong guesses.
  • Real catch: I said "student" while my repo said "learner". The glossary settles it.
  • It's not only documentation: CLAUDE.md points agents at GLOSSARY.md. The change is in PR #33, which is open with auto-merge on and not yet merged as I write this. Check its state before you say "merged".
  • Rule I added: never write "progress" alone. Say "learning progress" or "career advancement".

3. Show me a bounded context in your project. (Lesson 3)

  • One AI, two roles: mentor and maintainer.
  • Mentor: teaches the learner, never asks personal questions, protects privacy (mentor/MENTOR.md).
  • Maintainer: changes the curriculum, must pass tests/lint.py and tests/harness.py (CLAUDE.md).
  • Same repo, same AI, different rules and language. That's where the line is.

4. You can't read all the code an agent writes. How do you review it? (Lesson 4)

  • Pin today's behaviour with a characterization test, let the agent change the code, rerun and compare.
  • Put a seam where the code calls the outside world, so tests run on recorded data: fast and repeatable.
  • Separate timing check for speed, because pin tests check behaviour, not speed.
  • If it's worse on either, roll back.

5. What are the limits of that approach? When would you not trust it?

  • A characterization test records what the code does, not what it should do (InfoQ summary of Feathers). It pins existing bugs too.
  • So a green result means "unchanged", not "correct".
  • Tests only cover what I pinned. I choose the area around the change first.
  • Real example of a rule enforced by tests, not words: the harness runs every lesson's commands in a clean container.

6. How do you keep AI-written code good? Forty-five seconds. (Lesson 5)

  • Before: deep modules, one place per fact, one written language.
  • After: pin and compare, with a seam so it's fast, plus a timing check.
  • One real example: the harness stops an agent quietly breaking a lesson.
  • One-page reference: four habits.
