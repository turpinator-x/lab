Changing code you don't fully understand

Why this matters for agent work

An agent can change a lot of code fast. You won't understand all of it. So how do you know the change didn't break something? You don't read every line. You pin down what the code does now, then check that it still does it.

Tool 1: the characterization test

A characterization test checks what the code actually does today, not what it should do. Feathers coined the term. After a change, you rerun them and see whether anything unexpectedly moved. (InfoQ summary of Feathers' idea.)

Feathers' advice on where to start: write tests around the area you are about to change, then around the specific things you will change. If you are moving code, test that it is still connected properly.

Tool 2: the seam

A seam is a place where you can change behavior without editing in that place. You use one to cut a slow or risky dependency out of a test. (Fowler, Legacy Seam.)

Fowler's example: a price calculation calls a slow, costly shipping service. Pass the shipping function in as a parameter, and a test can hand in a fake that returns a fixed answer. The place where you choose real or fake is the enabling point.

Link to Lesson 1: a seam is where a module's interface lives. See the glossary.
