One language, and where it stops

Recap

You can now find a deep module (Lesson 1) and decide what belongs inside it (Lesson 2). Now the words. The names you use are part of the design.

Ubiquitous language

Ubiquitous language is a common, rigorous vocabulary shared by developers and the people who know the domain. It's rigorous because software doesn't cope well with ambiguity. It should show up in conversation, docs and code, and it should evolve as understanding grows. (Fowler, describing Evans.)

Why it matters for you: an agent reads your names. If you say "chain" in one place and "network" in another for the same thing, you invite wrong guesses, from people and from agents.

Where one language stops: bounded contexts

In a large system, one word can mean different things to different groups. Fowler's example: at an electricity utility, "meter" meant the grid connection, the customer connection, or the physical device. People smooth this over in conversation. Software can't. (Fowler, Bounded Context.)

The answer is to split the system into bounded contexts. Inside each one, the language is consistent. Between contexts, you are explicit about how terms map. Fowler says the dominant factor drawing the line is usually human culture: a different context begins where the language changes.

The glossary

A glossary writes the language down: one agreed word per concept, plus the words to avoid. It is the cheapest tool to keep humans and agents on the same page. See the glossary for this course.
